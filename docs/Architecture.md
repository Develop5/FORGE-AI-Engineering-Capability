# Architecture

## 1. Purpose

This document defines the architectural structure of FORGE, including its major components, responsibilities, boundaries, domain concepts, and interactions.

It describes how FORGE is structured independently of any specific user interface, external service provider, LLM provider, or implementation technology.

This document defines architectural responsibilities and boundaries. It does not define detailed implementation decisions such as programming languages, frameworks, APIs, deployment mechanisms, database technologies, or concrete third-party integrations.


## 2. Architectural Principles

### 2.1 Domain Capabilities Are Interface-Independent

FORGE domain capabilities are independent of the interface through which FORGE is used.

Capabilities receive domain inputs and produce structured domain results. They do not depend on a specific user interface or interaction mechanism.

This allows FORGE to be used through different interfaces and, in the future, as a reusable capability or Skill for other agents.

### 2.2 Workflow Control Is Separate from Domain Analysis

Workflow orchestration is separated from domain capabilities.

The Workflow Orchestrator owns execution state, workflow transitions, iteration control, user-interaction state, and decisions about the next processing step.

Capabilities perform their defined domain responsibilities and return results. They do not decide what capability executes next.

### 2.3 User Interaction Is Outside Domain Capabilities

Domain capabilities do not interact directly with users and do not remain active while waiting for user input.

User interaction is handled by the Interface and coordinated by the Workflow Orchestrator.

### 2.4 External Services Are Isolated from the Domain

Domain capabilities do not depend directly on concrete external systems, APIs, SDKs, or providers.

External systems are accessed through abstractions and adapters, allowing new source types or providers to be introduced without modifying domain capabilities.

### 2.5 LLM Providers Are Infrastructure Concerns

Capabilities that require LLM functionality depend on an LLM abstraction rather than on a specific model or provider.

The concrete LLM provider and model are selected and configured outside the domain capabilities.

### 2.6 Domain Results Are Interface-Independent

FORGE domain results are represented as structured domain concepts independently of how they are presented.

The Interface is responsible for deciding how a domain result is displayed to the user or consumer.

### 2.7 Domain and Infrastructure Are Separated

Domain capabilities do not own infrastructure concerns such as credentials, provider configuration, concrete external integrations, or persistence mechanisms.

Infrastructure implements the mechanisms required by the domain without becoming responsible for domain decisions.

## 3. Architectural Responsibility Map

The following map defines the architectural responsibilities of the main FORGE elements.

### 3.1 Interface

The Interface is responsible for interaction with the user or consuming agent.

Responsibilities:
- Collect user inputs, including references to external evidence.
- Collect user decisions and responses.
- Present Questions generated by FORGE.
- Present structured FORGE results.
- Represent execution states and errors to the user or consumer.
- Decide how domain results are rendered or otherwise presented.

The Interface does not:
- Execute domain analysis.
- Maintain FORGE workflow state.
- Decide which capability executes next.
- Access external evidence sources on behalf of domain capabilities.
- Depend on a specific FORGE domain capability implementation.

### 3.2 Workflow Orchestrator

The Workflow Orchestrator controls the lifecycle of a FORGE execution.

Responsibilities:
- Maintain the logical execution state.
- Validate inputs before invoking capabilities.
- Invoke capabilities with the required domain inputs.
- Process capability results at workflow level.
- Decide which capability executes next.
- Control workflow transitions and iterations.
- Manage states in which user input is required.
- Resume execution after user input is received.
- Manage execution configuration.
- Decide how technical errors affect workflow execution.

The Workflow Orchestrator does not:
- Perform domain analysis that belongs to a capability.
- Decide the functional content of domain results.
- Interact directly with external source systems.
- Depend on a specific LLM provider or model.

### 3.3 FORGE Domain Capabilities

Domain capabilities perform the functional analysis responsibilities defined by FORGE.

They:
- Receive domain inputs.
- Execute their defined responsibility.
- Produce structured domain results.
- Preserve the domain information required by subsequent capabilities.
- May use shared abstractions such as the LLM abstraction or source abstractions.

Capabilities do not:
- Control workflow progression.
- Maintain execution state while waiting for user input.
- Interact directly with the user.
- Depend directly on concrete external systems, SDKs, or LLM providers.

The current domain capabilities are:
- Evidence Consolidation
- Requirements Discovery
- Clarification
- Traceability Analysis
- Coverage Analysis
- Improvement of Requirement Coverage

### 3.4 External Source Adapters

External Source Adapters isolate FORGE from concrete evidence sources and external systems.

Responsibilities:
- Retrieve content from external sources based on references provided to FORGE.
- Translate source-specific access mechanisms into the abstractions consumed by FORGE.
- Handle source-specific integration details.

Examples include adapters for:
- Jira
- Confluence
- File-based sources
- Future external evidence sources

Adapters do not:
- Perform FORGE domain analysis.
- Decide whether evidence constitutes a Business Requirement.
- Control workflow execution.

### 3.5 LLM Abstraction

The LLM Abstraction provides LLM capabilities to domain components without exposing provider- or model-specific details.

Responsibilities:
- Provide a provider-independent interface for LLM operations required by FORGE.
- Isolate domain capabilities from concrete LLM implementations.

The LLM Abstraction does not:
- Define FORGE domain decisions.
- Control workflow execution.
- Determine which LLM provider or model is used.

### 3.6 Infrastructure and Configuration

Infrastructure provides the technical mechanisms required to execute FORGE without becoming part of the FORGE domain.

Responsibilities include:
- Concrete external-service integrations.
- LLM provider integrations.
- Credential management.
- Provider and model configuration.
- Persistence mechanisms.
- Operational configuration.

Infrastructure does not own FORGE domain decisions or workflow decisions.





## 4. Architectural Boundaries

FORGE is structured around explicit boundaries between user interaction, workflow orchestration, domain capabilities, and infrastructure.

### 4.1 Interface ↔ Workflow Orchestrator

The Interface communicates with the Workflow Orchestrator using workflow inputs, user decisions, and structured execution results.

The Interface does not invoke domain capabilities directly.

The Workflow Orchestrator does not depend on how the Interface represents information.

This boundary allows FORGE to be used through different interfaces without changing domain capabilities.

### 4.2 Workflow Orchestrator ↔ Domain Capabilities

The Workflow Orchestrator invokes capabilities using their domain contracts and receives structured domain results.

Capabilities do not control workflow transitions or user interaction.

The Orchestrator owns execution state and decides what happens after a capability produces a result.

Capabilities may therefore be invoked independently of the complete FORGE workflow.

### 4.3 Domain Capabilities ↔ External Sources

Domain capabilities do not access concrete external sources directly.

Capabilities request the information required for their domain responsibility through source abstractions. External Source Adapters resolve those requests against concrete systems.

This allows new evidence sources to be introduced without modifying domain capabilities.

### 4.4 Domain Capabilities ↔ LLM

Capabilities that require LLM functionality access it through an LLM abstraction.

Neither the capabilities nor the Workflow Orchestrator depend on a specific LLM provider or model.

Provider and model selection belongs to infrastructure and configuration.

### 4.5 Domain ↔ Infrastructure

Domain responsibilities are independent of infrastructure mechanisms.

Infrastructure provides technical mechanisms such as persistence, credentials, external integrations, and provider-specific implementations.

Infrastructure must not introduce domain or workflow decisions into the domain layer.

### 4.6 Domain Results ↔ Interface

Domain results are produced independently of their presentation.

The Interface consumes structured domain results and determines how they are presented to the user or consuming agent.

No presentation-specific concerns are required by domain capabilities.


## 5. Domain Concepts

FORGE operates on a set of domain concepts that are exchanged between capabilities and preserved across the workflow.

The authoritative definitions of these concepts are maintained in `Glossary.md`.

The main domain concepts relevant to the architecture are:

- Evidence
- Finding
- Business Requirement
- Question
- Risk
- Specification
- Test Case
- Coverage Result

### 5.1 Domain Concept Ownership

Domain capabilities are responsible for creating or transforming domain concepts according to their defined responsibilities.

The Workflow Orchestrator is responsible for maintaining the execution state in which these concepts are processed, but does not redefine their functional meaning.

The Interface presents domain concepts but does not own their meaning.

Infrastructure does not own domain concepts.


## 6. Execution Model

FORGE execution is coordinated by the Workflow Orchestrator.

The Interface provides the initial input and subsequently provides user decisions or responses when required.

The Orchestrator maintains the execution state and invokes the appropriate domain capability according to the current workflow state.

A capability:
1. Receives the domain input required for its responsibility.
2. Performs its domain analysis.
3. Produces a structured domain result.
4. Returns control to the Workflow Orchestrator.

The capability does not determine which capability executes next.

The Orchestrator evaluates the result, updates the execution state, and determines the next workflow transition.

When user input is required, the Orchestrator returns the relevant structured information to the Interface. The Interface presents it to the user and collects the user's response. The Orchestrator then incorporates that response into the execution state and resumes the workflow.

A capability does not remain active while waiting for user input.

### 6.1 General Execution Pattern

The general execution pattern is:

Interface
→ Workflow Orchestrator
→ Domain Capability
→ Domain Result
→ Workflow Orchestrator
→ next capability or user interaction
→ ...

External source access and LLM operations are performed through their respective abstractions and adapters and are not part of the workflow control mechanism.

### 6.2 Execution State

The Orchestrator owns the logical state of the execution.

Persistence of that state is an infrastructure concern and does not transfer ownership of workflow state to the persistence mechanism.

This allows an execution to be paused, persisted, and subsequently resumed without requiring a domain capability to remain active.

### 6.3 Capability Independence

Capabilities are independently invocable domain operations.

They do not require the complete FORGE workflow to be active in order to perform their defined responsibility, provided that their required domain inputs are available.


## 7. External Dependencies

FORGE may depend on external systems and services to obtain evidence, provide LLM capabilities, or support infrastructure concerns.

External dependencies are isolated from the FORGE domain through explicit abstractions and adapters.

### 7.1 Evidence Sources

FORGE may obtain evidence from external sources such as:

- Jira
- Confluence
- File-based sources
- Other evidence sources introduced in the future

The Interface provides references to these sources.

Evidence Consolidation determines what content is required from those references. Source-specific adapters are responsible for retrieving and translating the external content into information that FORGE can process.

Domain capabilities do not depend directly on the APIs, SDKs, authentication mechanisms, or data representations of concrete evidence sources.

### 7.2 LLM Services

Some FORGE capabilities may require LLM functionality.

Capabilities access this functionality through the LLM abstraction.

The concrete provider, model, credentials, and provider-specific configuration are infrastructure concerns.

Changing the LLM provider or model must not require changes to domain capability responsibilities.

### 7.3 Infrastructure Services

FORGE may require infrastructure services for concerns such as:

- persistence;
- configuration;
- credential management;
- execution support;
- operational concerns.

These services support FORGE execution but do not own domain or workflow decisions.

### 7.4 Extensibility

New external evidence sources, LLM providers, or infrastructure implementations should be introducible through their corresponding abstractions or adapters without modifying the core domain capabilities, unless the new dependency introduces a genuinely new domain requirement.


## 8. Architectural Constraints

The following constraints must be preserved by any implementation of FORGE.

### 8.1 Interface Independence

Domain capabilities must not depend on a specific user interface or interaction mechanism.

### 8.2 Workflow Ownership

Workflow state, transitions, iteration control, and decisions about the next processing step belong to the Workflow Orchestrator.

Domain capabilities must not assume responsibility for workflow progression.

### 8.3 Domain Ownership

Domain concepts and domain decisions belong to FORGE domain capabilities.

Infrastructure and interfaces must not introduce or redefine domain decisions.

### 8.4 External System Isolation

Domain capabilities must not depend directly on concrete external systems, APIs, SDKs, or provider-specific implementations.

External integrations must be isolated through appropriate abstractions and adapters.

### 8.5 LLM Provider Independence

Domain capabilities must not depend directly on a specific LLM provider or model.

Provider and model selection must remain outside the domain.

### 8.6 Presentation Independence

Domain results must not contain presentation-specific concerns.

Interfaces are responsible for representing domain results to users or consuming agents.

### 8.7 Infrastructure Independence

Domain capabilities must not depend on concrete persistence mechanisms, credential stores, deployment mechanisms, or other infrastructure implementations.

### 8.8 Capability Independence

A capability must be able to perform its defined domain responsibility without requiring a specific user session or remaining active while waiting for user input.

### 8.9 Contract-Based Interaction

Interactions across architectural boundaries must use explicit contracts rather than relying on implementation-specific knowledge of the component on the other side of the boundary.


## 9. Evolution / Extension Points

FORGE is designed so that changes in interfaces, external integrations, and infrastructure can be introduced without requiring changes to the core domain capabilities.

### 9.1 New Interfaces

New interfaces or consuming agents may use FORGE through the Workflow Orchestrator without modifying domain capabilities.

Examples may include:
- Web interfaces
- APIs
- Agent-based interfaces
- Future Skill-based integrations

### 9.2 New Evidence Sources

New evidence sources may be introduced by implementing the appropriate source adapter.

The domain capabilities remain independent of the concrete source implementation.

### 9.3 New LLM Providers or Models

New LLM providers or models may be introduced behind the LLM abstraction.

The domain capabilities remain independent of the concrete provider or model.

### 9.4 Infrastructure Evolution

Persistence mechanisms, credential management, deployment mechanisms, and other infrastructure services may evolve independently of the domain.

### 9.5 Domain Evolution

Changes that introduce genuinely new domain requirements may require changes to domain capabilities and domain concepts.

Such changes must be evaluated as domain changes rather than treated as infrastructure or integration changes.

### 9.6 Reusable Capability

The architecture allows FORGE domain capabilities and their contracts to be reused independently of a specific interface or deployment mechanism.

This provides a foundation for future integration of FORGE as a reusable capability or Skill for other agents.


## 10. Deployment Considerations

The deployment architecture must preserve the architectural responsibilities, boundaries, and independence defined in this document.

Deployment decisions must not introduce coupling between domain capabilities and:

- a specific user interface;
- a specific external evidence source;
- a specific LLM provider or model;
- a specific persistence mechanism;
- a specific deployment platform.

### 10.1 Execution State

The logical execution state owned by the Workflow Orchestrator must be recoverable independently of the runtime lifetime of an individual capability execution or user interaction.

A capability must not need to remain active while waiting for user input.

### 10.2 Stateless Capability Execution

Domain capabilities should be executable without relying on a persistent user session or on process-local workflow state.

Any state required to resume a FORGE execution belongs to the execution state managed by the Workflow Orchestrator and its supporting infrastructure.

### 10.3 Infrastructure Isolation

Deployment mechanisms, persistence services, credential stores, external-service integrations, and operational infrastructure must remain outside the FORGE domain.

Infrastructure may change without changing domain responsibilities.

### 10.4 Replaceability

The deployment architecture should allow the implementation of interfaces, external source adapters, LLM providers, and infrastructure services to evolve independently of the domain capabilities.

### 10.5 Engineering Responsibility

This document defines architectural deployment constraints but does not prescribe specific deployment technologies.

Concrete decisions regarding packaging, runtime environments, containers, orchestration platforms, persistence technologies, networking, observability, CI/CD, and cloud or on-premises infrastructure belong to Engineering.
